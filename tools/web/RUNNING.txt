Start (setsid detaches it from the session, so closing the terminal does not stop it):

  cd ~/projects/cachedMoE
  DEEPMOE_MODEL_DIR=$HOME/models/DeepSeek-V4.1-Flash setsid nohup \
    python3 tools/web/server.py --max-context 65536 --port 8080 \
    --log build/web_serve.log > build/web_ui.out 2> build/web_ui.err &

Nothing else needs passing. `--exe` defaults to build/deepmoe (build/deepmoe.exe on
Windows), the model directory comes from DEEPMOE_MODEL_DIR, and the three switches
below are already the engine's defaults. The desktop app can start the same thing from
.claude/launch.json, which uses ${workspaceFolder} and `python3`.

Stop (BY PID ONLY)
------------------
  kill <server.py pid>          -- it takes the engine child with it

  Kill server.py FIRST and then check the engine is not a zombie. The engine is
  server.py's child and server.py sits in serve_forever() without ever waiting on it,
  so killing the engine alone leaves a defunct `deepmoe` behind -- and `pgrep -x
  deepmoe` matches a zombie, so the "is the GPU free?" check then reports a process
  forever (walked into on 2026-09-30: it looked like a wait, the GPU had been free the
  whole time). Judge it with `ps -o stat= -p <pid>` (Z = already dead), or just kill
  server.py and let it reap the child.

  Also make sure 8080 is released before restarting: while an old server still holds
  the port, the new instance spends 40 s loading the engine and then dies on bind,
  and you lose both.

One GPU job at a time
---------------------
  Only one `deepmoe` engine may exist at once, and the UI's engine counts as one.
  Stop it before any bench or ctest and start it again afterwards. Three concurrent
  engines froze the machine once.

Logs
----
  build/web_ui.out     server.py stdout (the ready banner)
  build/web_ui.err     server.py stderr
  build/web_serve.log  the engine's stderr (cache / IO / session decisions)

  web_serve.log really has content in it (Track PF, docs/p3_chat.md §8.1). It used to
  hold two lines, because core/log.h wrote to `FILE* stdout`: once serve hands stdout
  to the protocol, fd 1 points at stderr but that FILE* is fully buffered on a pipe and
  `emit` only flushed at >= Warn, so every log_info sat in an unflushed 4 KiB buffer and
  died with the process. The logger now has a process-level sink (serve calls
  `set_log_stream(stderr)`) and flushes every line: 26 lines at startup, plus one
  session-decision line per turn.

      [INF] session: prompt N tokens, history H, common prefix C -> reuse R (cold|extend|rollback|reset|gpu-recompute), S to prefill (gpu_prefill_min 512)
      [INF] session: S tokens prefilled on the GPU in T s (X ms/token)

  When a turn reports a slow `prefill ... ms/token`, look here first.

The GPU load strip (added 2026-09-30, commit 517e664)
-----------------------------------------------------
  Under #bar: GPU utilisation % (blue area, fixed 0-100 scale) + NVMe read rate
  (orange line, scaled to the window's peak, peak printed in the corner) + the numbers
  (utilisation / clock / disk read / GTT / temperature / power). One sample a second,
  four minutes of history, polling paused while the tab is hidden. The source is
  server.py's own sampling thread (amdgpu sysfs + the read deltas of every nvme*n*
  device in /proc/diskstats) over /api/gpu, and it does NOT queue behind the engine --
  it keeps moving while the engine is busy, which is the whole question it answers: is
  the GPU busy right now, or the disk?

  Reading it: during decode, GPU 26-37% + disk 2.4-3.5 GB/s is normal (NVMe-bound).
  A 600 MHz clock is idle, ~2.9 GHz is running. High GPU + low disk is prefill's
  compute stretch.

The second read source
----------------------
  server.py finds it itself (`find_mirrors()`): a copy at the same path on another
  drive that carries a deepmoe_manifest.json. That is why the command above has no
  --mirror, and why the banner's `read sources 2` is not something anyone passed.
  On this machine that is /mnt/deepmoe2/models/DeepSeek-V4.1-Flash, mounted read-only.

    * off:              --no-mirror-auto
    * somewhere else:   --mirror DIR   (given explicitly, it does not auto-detect)
    * the ENGINE still defaults to one drive: `deepmoe serve` without --mirror is
      byte for byte main's behaviour. Auto-detection lives only in the web UI layer,
      because that is the process a user walks up to.

  find_mirrors() runs ONLY at startup. If the drive comes back after the server is up,
  restart the server or it stays on one source.

  Startup is ~2 s slower on purpose: the weight probe now warms up for 1 s before
  measuring for 1 s. A USB4 enclosure that has been idle takes ~1 s for its first read,
  and without the warm-up that read IS the whole 1 s window, so a 3.77 GB/s drive
  measures 0.03 GB/s and weighted routing hands it 0.0% of the bytes -- the second
  drive would be plugged in for nothing.
  DEEPMOE_MIRROR_PROBE_WARMUP_MS=0 restores the old behaviour.

  The engine-side mirror health gate (Track D4) is still there: it test-reads the
  pinned weights from the mirror at startup and drops the mirror if that fails, and it
  drops a source after three consecutive I/O errors at run time. So the banner's
  `read sources N` is the number of sources actually being read after the gate. Pull
  the drive and you get `read sources 1` plus a warning, not a crash.

  Two things about the mirror that were measured and LOST, recorded so nobody retries
  them (docs/p4_dual_source.md §10, STATUS §3):
    * DEEPMOE_MIRROR_KEEPALIVE_MS=15 -- a 4 KiB keep-alive read while the mirror is
      idle. 3,052 pokes, zero errors, +0.15%, the split bit-identical. The drive was
      never asleep: its typical idle gap is 59 ms and the slowest P0 in a whole cell
      is 19.84 ms.
    * DEEPMOE_MIRROR_STATIC_SPLIT=0.44 -- force the split open-loop to the bandwidth
      ratio. The split really did reach 44.0%, and it was -2.68% (stall 95.1 -> 100.9).
      28.5% is not routing failing to reach 44%; 44% is simply worse, because once a
      layer's burst is spread out both drives have to climb their ramp every layer and
      decode waits on the slower of the two.

  Reading a per-source latency: use the `src[]` line's P0 counters, not the mixed
  mean. The mixed mean crosses two priority classes -- P0 (what decode waits for) and
  P3 backfill (idle) -- and the mirror carries ~75% of the backfill, which is preempted
  by P0 and so waits 1.1-1.3 s. On the main drive backfill waits 1.1 s too. P0 alone:
  4.5 ms against 3.8 ms, a factor of 1.19 (Track D6, docs/p4_dual_source.md §10).

Things that no longer need passing
----------------------------------
  --cache-slots        Track H1a: `auto` caps itself at 5,000 slots
                       (DEEPMOE_CACHE_SLOT_CAP adjusts it, 0 disables), and after
                       building the slab pool it submits an empty command buffer to
                       probe; if that is rejected it drops 200 slots and rebuilds, up
                       to 5 times.
  --gpu-prefill-min    Track PF, docs/p3_chat.md §8: the engine defaults to
                       gpu_prefill_min = 512 (runtime/session.h) and server.py passes
                       nothing. A 1,118-token new prompt on a warm 5,000-slot cache:
                       168.8 s -> 28.6 s (25.6 ms/token, 5.9x). A continuation
                       (reuse > 0) reaches the GPU too, via "throw the reuse away and
                       re-prefill the whole prompt when the reuse is not worth it"
                       (--gpu-prefill-speedup, default 6.0, <= 1 disables): a
                       1,514-token second turn went 70.5 -> 35.5 s (2.0x).
                       --gpu-prefill-min 0 restores the old behaviour (that 0 used to
                       be a no-op; Track PF fixed it in the same change).
  clearing .pkv        Track H1b: a failed restore -- allocation refused, corrupt,
                       wrong size, any error code -- is a warning plus a cold prefill,
                       the turn finishes normally, and the bad .pkv deletes itself
                       (docs/p4_kv_ux.md §5.2). It used to be fatal: under the default
                       cache size path A fills with the expert cache (`slab pool: path
                       A full after 34 slabs`), the restore could not get memory, and
                       `serve: kv-disk restore failed: internal: vkQueueSubmit2 failed
                       (-2)` killed the turn outright.
                       Not fatal is not the same as recovered: with path A full the
                       restore still cannot get memory and that turn pays a full
                       prefill (STATUS §7 item 2 (2)).

                ~/.cache/deepmoe/web_chat/ here; %LOCALAPPDATA%\deepmoe\web_chat on
                Windows. One file per session name, replayed on a page refresh or a
                server restart.
                Until 2026-10-01 the Linux fallback was the repo tree itself
