deepMoE web UI —— 正在运行的实例
================================

打开： http://127.0.0.1:8080/

镜像（第二个读源）：**开，而且是自动找到的**（Track D5，docs/p4_dual_source.md §9）。
用户把同一块 J.ZAO SSD 换进 **USB4 盒子**之后，Windows 枚举成 **`BusType NVMe`**
（PCIe 隧道，**没有 UAS、没有 RTL9210**）—— D2/D3/D4 四次杀死引擎的那一层整个不在了。
**12 个 A/B cell 零错误**，`y_turns` **+9.4%**、`long_turns` **+4.63%**、两条流 **+13.5%**，
`l3_ppl` **NLL 0.630051 逐位不变**。

⚠️ **D2–D4 的「这块 U 盘不要再试」要重新读**：坏的一直是**桥**，不是这块 SSD。
同一块 NAND 在 USB4 盒子里跑完 476 GiB × 12 个 cell，一条 win32 1117 都没有。

ℹ️ **`server.py` 现在自己找第二块盘**（`find_mirrors()`）：另一个盘上**同样路径**、
且有 `deepmoe_manifest.json` 的那份拷贝。所以下面的命令**没有 `--mirror`**，
横幅里的 `read sources 2` 是它自己找到的。
* 关掉：`--no-mirror-auto`
* 指定别的：`--mirror DIR`（给了就不自动找）
* **引擎默认仍然是单盘**：`deepmoe serve` 不给 `--mirror` 与 main 逐字相同。
  自动检测只在网页 UI 这一层，因为它是用户走到机器前时正在跑的那个进程。

ℹ️ **启动比以前慢 ~2 秒**，是故意的：权重探针现在**先热身 1 秒再测 1 秒**。
一块空闲过的 USB4 盒子第一个读要 ~1 秒，不热身的话 1 秒窗口整个就是那一个读，
E: 会被测成 **0.03 GB/s**（实际 3.77），加权路由只给它 **0.0%** 的字节 ——
**第二块盘就白插了**。`DEEPMOE_MIRROR_PROBE_WARMUP_MS=0` 回到旧行为。

ℹ️ 引擎侧的镜像健康闸（Track D4）仍然在：启动时从镜像试读 pinned 权重、失败就摘镜像单盘跑，
运行期连续 3 次 I/O 错误也动态摘源。**横幅的 `read sources N` 是过闸之后真正在读的源数。**
盘拔了就是 `read sources 1` + 一条 warning，不是崩溃。

✅ **`--cache-slots` 已经不用给了**（Track H1a 生效，本实例就是这样起的）：
`auto` 自己封顶到 5,000 槽（`DEEPMOE_CACHE_SLOT_CAP` 可改，0 = 关），
并且建完 slab 池先提交一个空命令缓冲探一下，被拒就退 200 槽重建（最多 5 次）。
本次就绪横幅：`expert cache 87.6 GiB (5000 slots)`。

✅ **GPU prefill 现在默认开着，不用给 `--gpu-prefill-min`**（Track PF，docs/p3_chat.md §8）：
引擎默认 `gpu_prefill_min = 512`（`runtime/session.h`），`server.py` **什么都不传**。
1,118-token 的新 prompt 在 5,000 槽热 cache 上 **168.8 s → 28.6 s（25.6 ms/token，5.9×）**。
续写（reuse > 0）也上 GPU，靠的是「reuse 不值钱就扔掉、整个 prompt 重新 prefill」这条规则
（`--gpu-prefill-speedup`，默认 6.0，`<= 1` 关）：1,514-token 的第二轮 **70.5 → 35.5 s（2.0×）**。
要关掉回到旧行为：`--gpu-prefill-min 0`（这个 0 以前是空操作，Track PF 一起修了）。

✅ **`.pkv` 也不用在重启前清了**（Track H1b 生效）：恢复失败——分配被拒 / 损坏 / 尺寸不符——
是一条 warning + 冷 prefill，那一轮照常跑完，失败的那份 `.pkv` 被删掉。
本次启动前仍然顺手清了一次，日志里 `serve: restored 374 tokens from kv disk` 是之后写的。

  ✅ **这个文件现在真的有东西了**（Track PF，docs/p3_chat.md §8.1）：以前它只有两行，
  因为 `core/log.h` 写的是 `FILE* stdout`，而 serve 把 stdout 让给协议之后 fd 1 虽然
  指向 stderr，那个 `FILE*` 在 pipe 上是**全缓冲**的、`emit` 只在 `>= Warn` 时 flush ——
  每条 `log_info` 都躺在没人 flush 的 4 KiB 缓冲里，进程被 `Stop-Process` 杀掉时一起没。
  现在 logger 有进程级 sink（serve 调 `set_log_stream(stderr)`）并且**每行 flush**，
  开机就有 26 行，而且**每一轮对话都有一行 session 决策**：

      [INF] session: prompt N tokens, history H, common prefix C -> reuse R (cold|extend|rollback|reset|gpu-recompute), S to prefill (gpu_prefill_min 512)
      [INF] session: S tokens prefilled on the GPU in T s (X ms/token)

  `预填充 … ms/token` 那一行慢的时候，先看这里。

.pkv 前缀 KV 缓存
-----------------
  目录  %LOCALAPPDATA%\deepmoe\kv\D__models_DeepSeek-V4.1-Flash

  ✅ **不用再在重启前清空了**（Track H1b，本实例的 exe 已经带上）：`.pkv` 恢复失败——
  分配被拒 / 损坏 / 尺寸不符，任何错误码——现在是一条 warning + 冷 prefill，
  那一轮照常跑完，失败的那份 `.pkv` 自己被删掉。见 docs/p4_kv_ux.md §5.2。

  它以前是致命的：默认 cache 大小下 path A 会被 expert cache 占满
  （`slab pool: path A full after 34 slabs`），恢复拿不到显存就报
  `serve: kv-disk restore failed: internal: vkQueueSubmit2 failed (-2)`，
  而这个错误**直接杀掉那一轮对话**（抛进 tools/chat.py:186）。

  注意「不致命」不等于「能恢复」：path A 满时恢复仍然拿不到显存，
  那一轮付完整 prefill（STATUS §7 第 2 项的 ②）。要手动清的话还是这一行：

      Remove-Item "$env:LOCALAPPDATA\deepmoe\kv\D__models_DeepSeek-V4.1-Flash\*.pkv"

  ℹ️ **D6 把一个误读修正了**（`docs/p4_dual_source.md` §10）：
  上面「读源」那一栏写着「E: 的 mean lat 是 D: 的 5–6 倍」——**那个平均数混了两个优先级类**。
  routed 的是 P0（decode 等的那些）和 P3 backfill（空闲回填），而 **E: 扣着 75% 的 backfill**，
  backfill 被 P0 抢占所以它等 **1.1–1.3 秒**——**D: 的 backfill 一样是 1.1 秒**。
  **单独看 P0：E: 4.5 ms，D: 3.8 ms，只差 1.19 倍。**
  所以 `status.json` 的 `src[]` 行现在多了一行：**每源的 P0 计数器 + 空闲间隔**。
  看盘快不快，**看那一行的 `P0 ... mean lat`**，不要看上面的混合均值。

  ℹ️ **两个新开关，都默认关，都测过且输了**，写在这里只是为了别再试一遍：
  * `DEEPMOE_MIRROR_KEEPALIVE_MS=15` —— 镜像空闲时发 4 KiB 保活读。
    3,052 次 poke、零错误、**+0.15%**，分流逐位不变。盘根本没睡：
    E: 典型空闲只有 **59 ms**，而一整个 cell 最慢的 P0 是 **19.84 ms**。
  * `DEEPMOE_MIRROR_STATIC_SPLIT=0.44` —— 按带宽比开环压分流。
    分流真的到了 44.0%，然后 **−2.68%**：stall 95.1 → 100.9。
    **28.5% 不是路由够不到，是 44% 本来就更差**：一层的突发摊平之后
    **每层要在两块盘上各爬一次坡**，而 decode 等的是一层里最慢的那个。

  ⚠️ **本轮遇到一次瞬时的 E: 掉线**（1 / 11 个带镜像的引擎进程）：
  `l3_ppl` 第一次跑的 warm-cache backfill 途中报 `win32 433 / 55`，
  运行期闸连续 3 次摘源、单盘跑完、**NLL 仍然 0.630051**，立即重跑零错误。
  **USB4 把 D2–D4 那个码的概率压得很低，但没压到零。**
  这就是闸存在的理由：盘掉了是一条 warning 加一次降级，不是一次崩溃。
