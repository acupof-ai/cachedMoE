## 0. 结论（先看这段）

owner 的命题是"streaming 还有很多玩法——最后四层总能提前取到，**只要我们知道它要什么**"。
在真实 trace + 诚实带宽模型下测完 80 余种策略配置、共 253 次完整 replay，答案是：

| | 结论 |
|---|---|
| **知道要什么，值多少？** | 值很多。全知预取在 C=4,500 把 5.38 → **8.05 tok/s（+50%）**，配全知淘汰到 **10.83（+101%）** |
| **可实现的预测器够不够？** | **不够，而且差得远。** 在 4,500 / 5,711 槽下，Markov、token-id 表、token 内共现、隐状态 lookahead(d=1..8) **全部净负或持平**，最好的一个是 +0.8% |
| **需要多准才能翻正？** | **precision = 1.00。** 精度 0.9 仍然比不预取慢 **15%**（5.47 vs 6.45 @ C=5,711）。不是 0.9，是 1.00 |
| **"最后四层"特殊吗？** | **不特殊。** 逐层 LRU 命中率 0.856–0.918 几乎是平的，第 36–39 层是 0.884–0.889；全知只预取最后 4 层只值 **+5.5%**（5.38 → 5.68） |
| **整层常驻（pin）呢？** | **一律变差**，pin 越多越差（C=4,500 pin 最后 4 层：5.38 → 4.64，−14%） |
| **那什么有用？** | 两件事，都不是预测：**淘汰策略**（Belady 上限 +42%）和**带宽**（9 GB/s → +40%） |

**根因一句话**：demand miss 本身每 token 就要 95–106 ms 盘时间，而计算窗口只有 80 ms。
盘**不是有空闲产能可以拿来投机**——它已经欠着 25 ms 的债。任何一字节的错误预取都是
直接加到 stall 上的净亏损。**浪费预算是负数。**

## 1. 模型（写明白，好让别人推翻）

### 1.1 时间

- 每 token 40 层，一层 `T_layer` = **2.0 ms** GPU 计算 → 每 token **80 ms** 计算窗口。
- 第 L 层的路由在第 L 层**开始计算的那一刻**才知道（planner 不能提前看）。
- 第 L 层的 demand miss 让 GPU **原地停住**，直到 6 个 expert 全部落地。
- `tok/s = 1000 / (80 + stall_ms_per_token)`——按任务书给的口径，不是 design §3.1 的
  42 ms 常驻项口径，两者不可直接比较（见 §8 的说明）。

### 1.2 盘

一个 expert 18,800,640 B。盘是**一个 work-conserving 服务器**，4.5 GB/s
（design §9.2.1 实测 4.5–4.75）：

```
S   = 18.8 MB / 4.5 GB/s = 4.178 ms    # 一个 expert 占的盘时间
```

- 单发一个 expert → 4.18 ms 后落地，对得上 §9.2.1 实测的 4.0–4.7 ms 单发延迟；
- 盘饱和时 → 每 4.178 ms 吐一个 expert，就是 4.5 GB/s。
- **QD 8 与 4 MiB chunk 怎么进模型**：QD 8 时盘是带宽受限的，并发只改变"谁先完成"，
  不改变"每秒完成几个"，而且一层要等齐 6 个才能算。所以并发折进带宽这一个数；
  **4 MiB chunk 进模型的方式是服务量子** `Q = 4 MiB / 4.5 GB/s = 0.932 ms`：
  demand 抢占排队中的 prefetch 是立即的，抢占**正在服务**的 prefetch 要等一个 chunk，
  不是等一整个 expert。这是 prefetch 的固定队头代价。
  `--quantum-ms 4.178` 可以退化成"整 expert 不可抢占"的悲观界，§7 给了这条敏感性。
- 优先级：demand > prefetch；排队中的 prefetch 被 demand 命中会**升级**为 demand
  （不重新计时，已传的 chunk 不丢）。

### 1.3 planner 与计费

- planner 最多持有 256 个未完成 prefetch（队列项是描述符不是 buffer），并在**每个 token
  边界重新规划**：尚未开始传输的 prefetch 被取消。
- **字节按盘真正干过的活计费。** 被取消的、或者一直排在队尾没轮到的 prefetch **不计费**。
  这一条很重要：不这么算会把预取策略冤枉成比实际更糟。
- prefetch 落地时**真的进 cache**，占一个槽、淘汰掉别的东西（= `cache_sim` 的
  `--probe-position head`；`tail` 是自毁写法，见 `docs/route_trace.md` §8）。

### 1.4 指标

| 指标 | 定义 |
|---|---|
| `hit` | 请求发生时**已驻留** = GPU 没等。预取策略里它包含"预取已落地"的槽 |
| `cold_hit` | 同上但扣掉预取填进来的，= 纯驻留贡献 |
| `stall ms/tok` | GPU 真正停住的时间 |
| `drive util` | 盘忙时间 / token 墙钟（80 + stall） |
| `idle ms/tok` | 盘完全空转的时间——**这就是"没用上的机器"** |
| `overlap ms/tok` | 盘忙且 GPU 也在算的时间 = 藏在计算窗口下面的盘活 |
| `MB used` / `MB wasted` | 后来真被用上的 / 预取了却被淘汰或没用上的字节 |

> **`MB used` 怎么读**：它是"最终被用上的字节"，**不是"有效功"**。一个污染 cache 的
> 预取策略会把热槽挤掉，于是同一个 expert 被 demand 重取好几遍——每一遍都算 "used"。
> 所以 §4 里 `MB used` 从 476 涨到 820 不是"干了更多有用的活"，而是**同样的活干了 1.7 遍**。
> 判断策略好坏要看 `stall` / `tok/s`，`MB used` 的上涨是污染的读数。

### 1.5 数据切分与校验

- 40 个 prompt 按 prompt 切：**前 28 个（20,198 token）训练**，**后 12 个（7,201 token）
  测试**。切分以 prompt 为单位，不切断任何一条 prompt。
- 所有策略（包括 LRU / Belady 基线）都在**同一个测试集**上报，可比。
- cache 用训练集最后 2,000 token 的 demand-only LRU 回放预热，测试从热态开始。
- **交叉验证**：本文的 replay 在全量 trace 上给出 LRU 命中 **0.8903 @ 4,500 /
  0.9219 @ 5,711**；直接跑 `tools/cache_sim.py --policies lru --prefetch-depths 0`
  得到 **0.8903 / 0.9219**——两个独立实现逐位一致。
  （任务书里的 0.905 应该来自另一组 `cache_sim` 参数；以实测的 0.8903 为准。）

### 读这张表

1. **"demand only" 那几行把没用上的机器写在脸上**：`idle 80.0`，也就是**整个计算窗口
   盘都在空转**。demand-only 的定义就是零重叠——盘只在 GPU 等它的时候才动。
   每 token 有 80 ms × 4.5 GB/s = **360 MB 的免费盘产能被扔掉**。
2. **但这 360 MB 不够。** C=4,500 时 demand miss 要 476 MB / 105.7 ms 盘时间，比
   80 ms 的窗口还多。所以全知预取也只能把 util 拉到 0.851、idle 压到 18.5 ms，
   剩下 44.3 ms 是**带宽债**，不是调度问题。全知 + Belady 之所以能到 10.83，是因为
   Belady 先把字节数从 476 MB 砍到 227 MB，**然后**才轮到预取去藏它。
3. **"最后 N 层总能提前取到"——能，但不值钱。** 即使给它完美知识，只预取最后 4 层在
   C=4,500 只值 +5.5%（5.38 → 5.68），最后 8 层 +11.6%。原因是最后 4 层只占 10% 的请求，
   而且（见 §5）它们的命中率并不比别的层差。
4. **逐层 quota 一律更差**（−4.0% / −4.0% / −2.9%），Q2 的重用距离结论是对的：全局池更好。

## 3. 预测器质量（逐层 recall / precision，测试集）

`recall@K = |预测 top-K ∩ 实际 top-6| / 6`，`precision = 同样的交集 / K`。

| token-id 表 | 6 | 0.352 | 0.412 | 0.312 | 0.339 | 0.335 | **0.364** | 0.352 |
| 隐状态 lookahead d=1 | 6 | 0.674 | 0.501 | 0.654 | 0.708 | 0.764 | **0.768** | 0.674 |
| lookahead d=3 | 6 | 0.532 | 0.268 | 0.525 | 0.562 | 0.645 | **0.566** | 0.532 |
| lookahead d=4 | 6 | 0.491 | 0.196 | 0.488 | 0.517 | 0.604 | **0.507** | 0.491 |
| lookahead d=8 | 6 | 0.383 | 0.040 | 0.364 | 0.390 | 0.464 | **0.385** | 0.383 |
| lookahead d=1 | 16 | 0.855 | | | | | 0.935 | 0.321 |

**明确回答"最后四层是不是可预测"**：

- **是，但只对隐状态 lookahead，而且只在短 lead 上。** d=1 时 L36–39 的 recall@6 = **0.768**
  ——全层最高，深层确实比浅层好预测（L0–9 只有 0.501）。
- **不是，对任何不需要隐状态的方法。** Markov 与 token-id 表在 L36–39 只有 **0.29–0.36**，
  和它们在别的层一样差。深层没有额外的静态结构可挖。
- d=1 的 lead 只有 **2 ms**，一次取要 4.18 ms——**来不及**。把 lead 拉到 d=3/4（6–8 ms，
  刚够）时 recall 掉到 0.53/0.49，d=8（16 ms）掉到 0.38。
  **精度和提前量是互斥的**，这就是 lookahead 预取在 §4 里翻不了正的机制原因。
- token-id 表覆盖率只有 **0.690**（训练集里出现 ≥ 4 次的 token 才建表，1,022 个）。

1. **在 4,500 / 5,711 槽下，最好的预取策略是 +0.1% ~ +0.8%，在噪声里。** 稍微加大 K

2. **预算（budget）确实是唯一让预取不亏的旋钮**：`lookahead d=3 K=6 预算 2`

   这是全文唯一一个可实现的正收益，而且只有 3%，离 11.39 的天花板还差得远。
4. **Belady 淘汰 + lookahead 在 C=8,000 是 +10.9%（9.19 tok/s）**——但 Belady 不可实现，
   这行只是用来说明**淘汰这个杠杆比预取大**：同样的预测器，换个淘汰就从 +3.1% 变 +10.9%；
   而在 C=4,500 它是 −41.8%（Belady 会立刻淘汰刚落地的预取，因为它"下次使用很远"）。

## 5. 层粒度常驻与静态热集（owner 的 (g) / (i)）

一整层 = 384 × 18.8 MB = **7.22 GB = 384 槽**。

## 6. 整层 streaming 的带宽盈亏平衡（owner 的 (h)）

"在 token 的 80 ms 里把整整 N 层流进来"要多少带宽：

| N 层 | 字节 | **80 ms 内流完需要** | 4.5 GB/s 要多久 | 9 GB/s（第二块盘） | 30 GB/s（假想层） |
|--:|--:|--:|--:|--:|--:|
| 1 | 7.22 GB | **90.2 GB/s** | 1,604 ms | 802 ms | 241 ms |
| 2 | 14.44 GB | **180.5 GB/s** | 3,209 ms | 1,604 ms | 481 ms |
| **4** | **28.88 GB** | **361.0 GB/s** | **6,417 ms** | 3,209 ms | 963 ms |
| 8 | 57.76 GB | **721.9 GB/s** | 12,835 ms | 6,417 ms | 1,925 ms |

**所以"最后四层能不能在 80 ms 内全取进来"的字面答案是：需要 361 GB/s，比这台机器的
LPDDR 总带宽（~217 GB/s）还高 1.7 倍。** 整层 streaming 在任何可预见的存储层级上都不成立
——即使是 30 GB/s 的假想层，一层也要 241 ms，是整个 token 预算的 3 倍。

换个说法：整层常驻（§5）是这件事的**零带宽版本**，代价是槽；整层流式是它的**零槽版本**，
代价是带宽。两个极端都输给"按需 + LRU"。

**真正有意义的带宽问题不是"流整层"，而是"流实际缺的那些"**：

| C | demand miss 字节/token | **零 stall 需要** | 4.5 | 6.0 | 7.0 | 9.0 | 12.0 | 14.0 GB/s |
|--:|--:|--:|--:|--:|--:|--:|--:|--:|
| 4500 | 476 MB | **5.95 GB/s** | 5.38 | 6.28 | 6.76 | 7.53 | 8.36 | 8.77 tok/s |
| 5711 | 337 MB | **4.22 GB/s** | 6.45 | 7.34 | 7.80 | 8.51 | 9.25 | 9.61 tok/s |
| 8000 | 183 MB | **2.29 GB/s** | 8.29 | 9.05 | 9.42 | 9.97 | 10.50 | 10.75 tok/s |

> "零 stall 需要"是**只有完美预取才能达到**的下界（把全部 miss 均匀铺到 80 ms 里）；
> demand-only 达不到它，因为 demand-only 没有重叠。这一列的用处是给出**加带宽的收益上限**。

- **C=5,711 时零 stall 只要 4.22 GB/s——低于这块盘的 4.5 GB/s。**
  也就是说在 5,711 槽上，**盘的带宽已经够了，缺的全是"提前发"这件事**。
  这正好是全知预取在 5,711 能打到 9.59（vs demand-only 6.45，+49%）的原因。
- C=4,500 时需要 5.95 GB/s，超出这块盘 32%，所以再完美的调度也剩 44 ms stall。
- 第二块盘（stripe 到 9 GB/s，design §3.1 已预留）：C=5,711 下 6.45 → **8.51（+32%）**，
  且不需要任何预测。

## 7. 需要多准才值得预取（关键实验）

把全知预测按精度降级：每层发 K 个候选，其中 `round(K × precision)` 个是真的，其余是该层
的随机 expert。字节量固定，只有"有没有用"在变。

| precision（K=6/层，满 lead） | C=4500 | C=5711 | C=8000 |
|--:|--:|--:|--:|
| 不预取（LRU） | **5.38** | **6.45** | **8.29** |
| 0.2 | 4.45 | 5.30 | 6.88 |
| 0.4 | 4.45 | 5.31 | 6.89 |
| 0.5 | 4.47 | 5.33 | 6.92 |
| 0.6 | 4.48 | 5.36 | 6.96 |
| 0.7 | 4.48 | 5.36 | 6.96 |
| 0.8 | 4.53 | 5.47 | 7.52 |
| **0.9** | **4.53（−16%）** | **5.47（−15%）** | **7.52（−9%）** |
| **1.0** | **8.05（+50%）** | **9.59（+49%）** | **11.39（+37%）** |
| 1.0，K=3/层 | 6.91 | 8.05 | 9.73 |

**盈亏平衡精度是 1.00。** 0.9 → 1.0 之间是一个 **+78% 的悬崖**（4.53 → 8.05）。

为什么这么极端，算一下就懂：K=6/层 × 39 层 = 234 个候选。precision = 0.9 意味着每层
0.6 个垃圾 = 每 token **23 个垃圾 expert = 98 ms 额外盘时间**。而计算窗口只有 80 ms，
demand 本身还欠着 25 ms。**浪费预算是负的**——每一个错误预取都是 4.18 ms 的净 stall，
加上它淘汰掉的那个热槽将来还要再取一遍。

这条曲线也解释了 §4：最好的可实现预测器（隐状态 lookahead d=1）precision = 0.674，
而且它的 lead 只有 2 ms；把 lead 拉到能用的 d=3 时 precision 掉到 0.532。
**0.53 落在悬崖的最底下。**

### 7.1 敏感性：不可抢占的盘

如果 4 MiB chunk 抢占不成立（demand 必须等完整个正在服务的 expert）：

| policy | C | chunk 抢占（0.93 ms 量子） | 不可抢占（4.18 ms 量子） |
|---|--:|--:|--:|
| LRU demand-only | 4500 | 5.38 | 5.38（不变，没有 prefetch 挡路） |
| 全知预取 + LRU | 4500 | 8.05 | 8.08 |
| lookahead d=3 K=4 | 4500 | 5.26 | **5.00** |
| lookahead d=3 K=4 | 5711 | 6.48 | **6.19** |
| lookahead d=3 K=4 | 8000 | 8.55 | **8.32** |

结论稳健：抢占粒度只影响**错**的预取（−3% ~ −5%），不影响 demand-only 也不影响全知。
本文正文用的是对 prefetch **更友好**的 chunk 抢占模型，所以上面的负结论不是模型偏见造成的。

## 9. 建议

### 9.1 不要实现的（有数据支撑的否定）

| 不做 | 依据 |
|---|---|
| 任何基于 expert 转移 / token-id / token 内共现的预取 | §4，全部 −2% ~ +0.2%，预测器 precision 0.30–0.35 |
| 隐状态 lookahead 预取（design §9.4） | §4，在 4,500/5,711 上 −0.1% ~ −12.6%；§7 的悬崖解释了为什么。**这条确认并加强了 Q4 早先的结论**，并给出了机制：不是 lookahead 不准，是浪费预算为负 |
| 整层常驻（pin 最后 N 层 / 最差 N 层 / 最偏斜 N 层） | §5，全部为负，最好的一行也是 −1.9% |
| 每层静态热集常驻 | §5，热 8 个 −0.5%，越多越差。与 `cache_sim` 的 `static-pin+lru` 结论一致 |
| 整层 streaming | §6，一层要 90 GB/s，四层要 361 GB/s |
| 逐层容量 quota | §2，−3.9% |
| 预测感知淘汰 | §4.1，±0.1% |

### 9.2 该做的（按性价比排序）

1. **先把 engine 的 planner 修到 LRU（正在另行处理的那 6.8 pt）。**
   这是全文最大的单项：engine 0.837 → 纯 LRU 0.890 @ 4,500，在本文模型里是
   5.38 tok/s 那一行；用 0.837 跑同一个模型是 ≈ 4.5 tok/s。**+20%，零风险，不需要任何预测。**
2. **扩容量，优先级高于任何策略。** 4,500 → 5,711 是 **+20%**，5,711 → 8,000 是 **+29%**，
   而且是所有策略里唯一一个同时抬高天花板的动作（§8 每一行都随 C 上升）。
3. **淘汰策略是第二大杠杆，值得单独立一条 track。** Belady 在 4,500 上是 **+42%**，
   在 5,711 上 +34%。本文只测了 LRU / quota / Belady；`cache_sim` 里还有 ARC、
   LFU-decay、score-aware 三种没有在**这个时间模型**下跑过。
   **具体建议：把 `cache_sim` 的 score-aware（用 top-16 的原始分数刷新 heat，
   §9.3）接进本文的 replay 跑一遍**——它是唯一一个用了 trace 里"近似命中"信息的
   淘汰策略，是最有可能吃到 Belady 那 42% 中一部分的候选。这是本文没做完的事。
4. **第二块 NVMe（stripe 到 9 GB/s）比任何软件策略都大**：C=5,711 下 +32%，
   C=4,500 下 +40%，无预测、无风险。design §3.1 已经预留了 stripe。

### 9.3 如果一定要上预取

**唯一有数据支持的配置**：`lookahead d=3, K=4, 预算 ≤ 2 个在途 prefetch`，
**且只在 C ≥ 8,000 槽时开启**。

- 预测收益 **+3.1%**（8.29 → 8.55 tok/s），**折半后的保守预期 = +1.5%**。
- 开启条件必须是运行时可判的：**当"最近 64 个 token 的 demand 盘忙时间 < 60 ms/token"
  时才允许发 prefetch**，否则关掉。这条比"队列深度 < N"更直接地对应 §7 的机制
  （盘有没有余量），而 `budget` 实验（§4）显示队列深度阈值本身只能做到不亏。
- 预期是这么小、开启条件这么窄，**我的建议是先不做**，把工程量放到 9.2 的 1–3 项上。

### 9.4 engine owner 该跑的 ablation（确认用）

按优先级，每条都是同一 binary、同一 script、轮换顺序、各 ≥ 8 turn：

| # | A/B | 预期（本文，已折半） | 证伪条件 |
|---|---|---|---|
| 1 | planner 修复前 / 后（hit 0.837 → ≈ 0.89） | **+10%** decode tok/s | 修好后 hit < 0.88 → 本文的 LRU 基线不适用于 engine，全部结论要重测 |
| 2 | `--cache-gb` 对应 4,500 / 5,711 / 8,000 槽 | +10% / +14% | 实测曲线比本文平 → cache 之外还有瓶颈，先查 §13.4 的分解 |
| 3 | 淘汰策略 LRU / score-aware（若实现） | +5% ~ +20%（Belady 上限 +42% 的一部分） | 无差别 → top-16 分数没有可用信息，Belady 的 42% 全在"未来"里，不可及 |
| 4 | 预取 开 / 关（仅当已在 8,000 槽） | +1.5% | 任何负值 → 按 §9.3 的开启条件关掉，本文预测该条件下不会为负 |

**顺序很重要**：1 不做完，2/3/4 的读数都没有意义。

## 10. 已知局限

1. **语料只有一条。** `traces/mixed` 的中文几乎全部来自本仓库的设计文档
   （`docs/route_trace.md` §6 已记为已知局限）。所有"预测器不准"的结论都是在这条
   语料上的。对话 / 文学体裁下 token-id 表的覆盖率与 recall 都可能不同——但 Markov
   与 lookahead 是与语料无关的结构性预测，那两条的结论外推性更强。
2. **测试集只有 12 个 prompt / 7,201 token。** 保持整条 prompt 是有意的（重用距离
   分布依赖它），代价是切分粒度粗。全量 trace 的 LRU 基线（§1.5）与测试集相差 0.4 pt，
   说明测试集不偏，但单条策略的 ±0.3% 差异应视为噪声——§4 里那几个 +0.1% 就是噪声。
3. **`T_layer` = 2.0 ms 是任务书给的，不是实测。** design §7.16.5 实测热步 81.5 ms
   （非 stall），大致吻合；但如果真实计算窗口更大（§15.1.1 的对话口径 90–100 ms），
   盘的相对余量会变大，§7 的悬崖会略微左移、§4 的预取结论会略微好转。
   **这是本文对预取最不利的一个假设，记在这里。**
4. **盘模型是单服务器 + 量子抢占**，没有建模真实 NVMe 的 QD 内乱序完成、读放大、
   SLC 缓存耗尽后的降速。§9.2.1 实测 4.5–4.75 GB/s 是平台值，长时间满负载可能更低
   ——那只会让本文的负结论更强。
5. **没有测 ARC / LFU-decay / score-aware**（`cache_sim` 里已有实现，但没有在本文的
   时间模型下跑）。这是 §9.2 第 3 条建议的由来，也是本研究最明确的未完成项。
6. **prefill 与 DSpark 不在范围内。** 本文只看 batch=1 的 decode 请求流。DSpark 的
   k-token verify 会把相邻 token 的 expert 并集摊薄（`docs/route_trace.md` §8 的
   `union_frac[k]`），那会**降低**每 token 的 miss 字节，等效于往表格右边（大 C）移动
   ——按 §4 的趋势，那正是预取开始转正的方向。**DSpark 落地后本研究值得重跑。**
