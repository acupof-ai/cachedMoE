# Track HG：host 写 flag、device 自旋等它 —— 另一种 device 侧 gate

**结论先写：NO-GO，但被关掉的不是合法性，是延迟。**
机制**成立**（不死锁、不 TDR、payload 可见、结果逐位正确），
**稳态最好 3.6 µs**（今天是 400 µs，快 111 倍），
但**只要 host 不是在几微秒内答上来，这一轮就固定要 ~5.5 ms**。
decode 的每一层 host 至少要花 95 µs（§3 的 53 的分解表），**一层都落不进那个快窗口**。
按 `40 × (400 − 实测)` 算：最乐观 **−23 ms/token**，现实 **−205 ms/token**。**是亏，不是赚。**

---

## 1. 为什么值得再问一次

§3 的 **48** 关掉的是 **workgroup ↔ workgroup** 的握手：两个 group（远低于 ~406 的常驻上限）
在 1,000 次往返里**第 3 次就超时**。共存不蕴含前进 ⇒ device 侧任务队列不合法。

§3 的 **53** 量出 gate 往返 **0.40 ms/层 = 16.0 ms/token**，其中 **265 µs 是驱动的**
（`vkQueueSubmit2` 99.5 + submit→GPU 起跑 ≈150 + fence 唤醒 ≈15）。
这 265 µs 一个 token 要付 **40 次**，理由只有一个：**命令缓冲在 gate 处被切开**，
因为 host 必须先读到 top-16 才知道要取哪些 expert。

**这一条问的是一个不同的机制**：不去掉 host，只去掉那一刀。
一个 workgroup 自旋等 **host 写的一个 uint**。依赖方向从此**指向 device 调度域之外**的
一个永远在跑的 CPU 线程 —— **48 的失效模式（等一个可能永远不被调度的同伴）按构造就不存在**。

## 2. 探针

`bench/probes/hostflag_probe.cpp` + `gpu/shaders/probe_hostflag.slang`，
复用 `probe_common.h` 的 bring-up（Track W）。

一个 command buffer 里 **40 轮**（= 40 层），每一轮：

```
[20–256 个 workgroup 的背景 compute]  →  barrier
kernel A：把 round 写进 host-coherent 的 Ctl[kReq]   →  barrier  →  timestamp
kernel B：1 个 workgroup 自旋等 Ctl[kFlag] >= round  →  barrier  →  timestamp
kernel C：读 host 写进 Ctl[kVal] 的 payload，对不上就置 kOutBad
```

host 线程轮询 `Ctl[kReq]`，睡 `service_ms`（0 / 1 / 5 ms，模拟命中 / 未命中），
先写 payload、再写 flag。两个 timestamp 之间就是**device→host→device 的往返**。

### 2.1 每一个等待都有硬上限，而上限是**算出来的**不是猜的

* shader 的自旋只由 `spin_limit` 次数封顶，没有别的出口；
* host **先用同一个循环标定** ns/iteration（`--max-spin-us` 除以它就是 `spin_limit`），
  所以那个上限落在**墙钟预算**上而不是一个拍脑袋的迭代数；
* **`rounds × max-spin-us` 被夹在 `--tdr-budget-ms`（默认 1500）之下** ——
  **TDR 数的是整个 packet，不是单个 dispatch**。
  这就是为什么这里的单次上限是**几十毫秒**而不是任务书里那半秒：
  40 轮 × 500 ms = 20 s，**必 TDR**；40 × 30 ms = 1.2 s，在 2 s 的窗口之内。
* host 自己等完成也有 deadline，队列卡住是**一行打印加退出**，不是挂死。

实际验证：atomic 那一档**在一个 command buffer 里自旋了 997 ms**（40 × 25 ms），
**驱动没有 reset**。夹在 1,500 ms 是对的。

### 3.1 三件独立成立的事

**(a) 机制成立。** 2,500+ 个 command buffer，**零 TDR、零 device 丢失、零提交失败、
零 payload 错误**。`kOutBad` 全表为 0：flag 之后 host 写的值**确实可见**。

**(b) 前进保证过了 —— 这是相对 48 的新事实。**
256 个背景 workgroup 常驻的同时，自旋的那个 workgroup **一次都没有超时**，
**3998/4000 轮是「自旋了之后才看到」**（`spins > 0`），也就是说它**真的观察到了
kernel 已经在跑之后 host 才写下的那个值**。
**48 的失效模式不复现**——因为依赖指向的是 CPU，不是同伴 workgroup。

**(c) 延迟是双峰的，而两个峰之间差 1,500 倍。**
p50 **3.6 µs**，p99 **5,598 µs**，中间几乎没有东西。一轮要么几微秒，要么 **~5.5 ms**。

### 3.2 那 5.5 ms 是什么 —— 两次尝试都排除了「我们的锅」

| 假设 | 怎么测的 | 结果 |
|---|---|---|
| host 的 WC 写没刷出去 | flag 之后补一个 `mfence` + 读回 | **无变化** |
| host 轮询线程凉了（睡过之后 CPU 核 / 缓存冷） | `hot` 档：service 期间**不停地读** `Ctl[kReq]`，模拟专职轮询线程 + I/O 线程分开 | **完全无变化**：1 ms 档 5532.2 vs 5532.4，5 ms 档 5534.5 vs 5552.6 |
| 是 warm-up | 按轮次拆开 | **第 1 轮永远 ~5.06 ms（398/399 超过 1 ms），第 40 轮 mean 1149–1519 µs（82–109/399 超过 1 ms）** |

**而且 1 ms 和 5 ms 两档的延迟完全一样（5532 vs 5553）。**
服务时间差 5 倍、延迟不差 —— 这说明它**不是一段延迟，是一个固定的刷新周期**：
device 侧那条相干读路径大约每 **5.5 ms** 才会真的重新去内存取一次那行。
host 只要没在**自旋启动后的头几微秒**之内答上来，这一轮就得等到下一次刷新。

**专职轮询线程救不了它** —— 这一条很重要，因为那是唯一一个"再写点代码就能修"的候选。

### 3.3 自旋方式：没有区别

busy 975.2 vs backoff（每次轮询之间插 64 步算术）961.0，p50 3.6 vs 3.8。
**±1.5%，在噪声里。**
（`s_sleep` 本身 Slang / SPIR-V 都发不出来，backoff 是能写出来的最近的替身。）

### 3.4 原子读 flag 是个陷阱，写下来免得下一个人踩

`InterlockedAdd(Ctl[kFlag], 0u, seen)` 看着是"最强的读"，实际 **76/80 轮在 30 ms 的上限上超时**。
原子即使加 0 **也是 read-modify-WRITE**：它把那一行在 device 自己的缓存里**弄脏**，
之后每一次轮询都由这条脏行回答，**host 的写永远进不来**，
而且回写的时候还可能**把 host 写的值盖掉**。
**要用 `globallycoherent` 的普通读，不要用原子。**

## 4. 判决

判据是 §3 的 53 定的那条式子：**省下来的 = 40 × (400 − 实测) µs/token**。

| 场景 | 实测 µs/层 | 40 × (400 − 实测) |
|---|---:|---:|
| 最乐观：空闲、host 0 延迟 | 975 | **−23 ms/token** |
| 现实：一层里 host 要花 ≥95 µs（53 的分解表） | 5,532 | **−205 ms/token** |
| 背景有 256 个 workgroup（= 真实 decode） | 2,885 | **−99 ms/token** |

**每一格都是负的。** 热步一共才 102 ms。

**要重开它，需要的不是代码，是那 5.5 ms 消失。**
如果稳态的 3.6 µs 能被每一层拿到，奖金是 **40 × (400 − 3.6) = 15.9 ms/token**——
那是 §7 第 4 项标价的那整块。但把它拿到手的前提是
**host 要在 device 自旋开始后的几微秒内答完**，
而 decode 的一层 host 侧最少 95 µs、未命中层 8,780 µs（53）。**够不着，而且差两个数量级。**

## 5. 留下了什么

* `bench/probes/hostflag_probe.cpp` / `gpu/shaders/probe_hostflag.slang`，
  编译进默认构建（`hostflag_probe` target），`--help` 不碰 GPU，所有等待有界；
* `bench/results/p4hg/hostflag_probe.csv`；
* 一条可复用的**安全纪律**：device 侧自旋的上限要按 **packet** 夹（`rounds × cap < TDR`），
  并且那个 cap 要**用同一个循环标定出来**，不能按迭代数猜；
* 一条**相对 48 的修正**：`48` 的「自旋等待在这台机器上 NO-GO」**只对 workgroup↔workgroup 成立**。
  **host 信号的自旋等待是合法的、安全的、正确的**，它输在延迟上，不输在前进保证上。
  下一个想做 device 侧 gate 的人不必再验这一条。
